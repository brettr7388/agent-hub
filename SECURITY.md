# Security

## Threat model

Agent Hub is a single-owner application for a trusted user's computer. Its login token protects the Hub interface from other users on the network. It is not a multi-user boundary or a sandbox for untrusted agents. By default, all Pips—including Guide, linked Pips, and team workers—use the user's normal CLI configuration and access: instructions, memory, settings, MCP servers, plugins, skills, permissions, and environment. Full-access Claude Pips use `--permission-mode auto` when supported; older CLIs fall back to `acceptEdits` plus `WebSearch` and `WebFetch`, while the inherit option uses existing Claude permissions and new tools may be denied in background runs. Consequential sends, posts, purchases, and deletes still require Hub approval cards under the existing prompt policy. Claude uses `--chrome` when available. A Pip can use the tools available to its CLI, and prompts and files it reads may be sent to the model provider. Review instructions, outputs, and proposed actions before proceeding.

Hub stores chats and settings locally. Keep the checkout, token, and backups private. **Private Pip** is optional and off by default; it seals instruction and tool discovery using the previous isolation controls. **Draft only** keeps plan/read-only restrictions, using a safe mode without MCP for Claude and a private HOME plus read-only sandbox for Codex. Neither mode makes arbitrary agent instructions safe. Linked and team-worker mode switches live in a Hub-side SQLite overlay; managed Pips keep their switches in Hub-owned metadata. Hub does not edit linked folder metadata; the CLI runs in the selected working folder normally and may create runtime files there.

## Approval requests and actions

Every Pip is instructed to stop before sending a message, DM, or email; making a public post; purchasing; deleting data; or changing an account setting. It must emit a fenced `agent-hub action approval_request` block containing a summary, details, and the exact payload, then wait for the owner. **Approve** and **Don't** buttons and 👍 return the exact approval or decline to that same Pip. They only communicate the owner's decision; they never execute the action. Malformed blocks are displayed as plain text.

This approval rule is a prompt policy, not transactional interception or an enforceable action boundary. A Pip can fail to follow it, and inherited hooks, plugins, browser tools, or other CLI capabilities may have broad access. Prompt injection remains possible, and the user's CLI permissions still apply. Claude's print transport cannot fully forward interactive native tool-permission prompts; a run may pause or refuse and ask through a Hub card. Codex `exec` provides no `--chrome` or dedicated append-system-prompt option, so Hub adds the rule to the prompt envelope while retaining the user's normal Codex configuration; full-access runs use a `workspace-write` sandbox with CLI terminal approval prompts disabled and inherit the configured network setting. Existing browser and computer tools depend on that CLI configuration; parity with ChatGPT's built-in tools is not guaranteed.

Never enter passwords in chat: chat text is stored locally and prompt content may be sent to the provider. Log in manually in a dedicated browser profile so the password does not enter chat. A full-access Pip running under your OS account may still reach that browser session, files, and the credential store using its normal CLI tools. Prompt injection can cause a full-tool Pip to call the OS vault CLI directly; Hub’s fill approval does not prevent this. For saved-login sites, use Private Pip for advice and operate the site yourself; Private Pip cannot automate Pip browser. Private Pip removes default integrations but is not an OS sandbox or an absolute vault barrier. Use Claude's 1Password integration where available. For browser work, prefer a dedicated Chrome profile without banking, health, or government accounts, and a separate test browser on work computers. The optional Pip browser is separate from inherited browser tools, including Claude in Chrome when available; neither is the only browser a full-access Pip may access. Pip browser is disabled for Private Pip and Draft only. Hub connects to Chrome through a remote-debugging pipe and a Hub-owned 0700 directory and 0600 Unix socket/proxy, with no public TCP DevTools listener. Other processes running as the same OS user may still control the socket or profile. Full-access Pips may be able to access browser sessions or other resources available to their CLI; do not assume passwords, cookies, or authenticated sessions are inaccessible.

If you reset a lost token, Hub commits session revocation before replacing the saved token hash. If writing the new auth file fails, the old token still works for a fresh login; rerun `python3 hub.py --reset-token`. If Hub stops after revoking sessions but before finishing the reset, current browser sessions are logged out; rerun the command to complete the reset and print a new token.

## Network model

Hub listens on loopback (`127.0.0.1`) by default. Non-loopback binding requires the explicit `allow_lan_bind` setting and produces a warning because it exposes the login interface to the local network. HTTPS origins configured for Tailscale Serve are accepted only when their requests arrive from loopback, as the Serve proxy connects locally. Use Tailscale Serve for tailnet-only phone access. Funnel, public port forwarding, and direct public exposure are unsupported.

Hub caps handlers at 48, allows at most eight concurrent unauthenticated connections per source IP and 16 overall, and reserves the remaining capacity for authenticated sessions. It recognizes complete session-cookie headers without blocking the accept loop. Header reads have a 10-second deadline; JSON bodies have 30 seconds; uploads have a total deadline of at least 30 seconds, scaled at 32 KiB per second. These controls bound slow requests; they are not protection against a hostile local process.

Tailscale Serve forwards connections from loopback, so its users share the per-source quota. For deployments with an additional configurable reverse proxy, cap upstream concurrency at 48 and its header deadline at 10 seconds as well; keep the upstream listener on loopback. Do not assume Serve itself supplies these limits. A valid Hub token grants broad access to the owner's chats and agents; do not share it.

## Reactions

👍 and ✅ mean approval of only the proposal in the reacted-to message; 👎 declines, and ❓ requests an explanation. On an approval request, the reaction sends the exact approval or decline to that same Pip, just as the card buttons do. These controls do not run the requested action. Malformed approval blocks remain plain text. Pips should acknowledge every approval, decline, or question.

## Group handoffs and routing

In a group you create, structured handoffs run automatically. A handoff requires a final standalone `@@handoff target-name: task` line outside quotes and code blocks; an ordinary `@name` mention does not delegate work. Hub strips the marker from visible text and gives the receiving Pip the full original request and sender message. Handoffs are limited to three per chain. A handoff routes context; it does not itself write files or send anything outside Hub. It does not change the recipient's engine, mode, or permissions; the receiving Pip's own settings continue to govern its actions. When group routing is ambiguous, Claude may classify the request in an isolated, tools-disabled call. Codex has no verified tool-free classifier mode, so Hub uses a deterministic fallback: the last responder if still in the group, otherwise the first Pip in the group.

## Exports

Exports include your chat text. Review before sharing — we redact obvious secrets but can't catch everything. Pattern screening reduces exposure but cannot guarantee that chat text, instructions, or other included content is free of sensitive information. Authentication and provider token files are excluded.

## Reporting a vulnerability

Please report security issues privately through GitHub's **Report a vulnerability** feature for this repository. Include the affected version, impact, and a minimal reproduction. Do not include live tokens, credentials, private chat content, or other users' data. We will acknowledge reports and coordinate a fix before public disclosure where practical.
